CheckNationalityClient 强制检查国籍（DidaAPI ONLY）
▼
作用：控制 ARI 和 Rate 场景下是否检查国籍限制。
ARI 场景：控制 ARI 接口是否检查国籍限制
Rate 场景：控制是否开启 Nationality Free 功能
  • 配置为否（默认）→ Nationality Free：国籍被过滤时直接返回报价，不执行 NationalityFilter
  • 配置为是 → 开启国籍限制：检查 RP 的售卖国籍是否匹配，不匹配的 RP 被过滤
位置：WolfV2 → 机构配置 → 国籍类
配置示例：渠道: DidaAPI，供应商: 429 (DaoLv)，国籍: ID，配置为 Yes → 该组合执行国籍限制检查
SubClientID 忽略国籍限制（NationalitySubChannelID）
▼
作用：为机构指定子渠道（SubChannel），应用于 ARI 和 Rate 两个场景。
JSON 结构：
{ "SubChannelConfigs": { "DidaOpaq": { "NationalitySubChannelID": { "None": [], // 不限制国籍 "International": ["2"], // 外宾：允许卖其他国籍 RP "Domestic": ["3"], // 内宾：只卖当前酒店国籍客人的 RP "China": ["4"] // 中宾：允许卖 CN, TW, HK 的 RP } } } }
NationalitySubChannelID 四档：
档位值含义 None空数组不限制国籍的渠道 International["2"]外宾：允许卖其他国籍 RP Domestic["3"]内宾：只卖当前酒店国籍客人的 RP China["4"]中宾：允许卖 CN、TW、HK 的 RP
忽略国籍触发条件（需同时满足）：
1
机构请求的供应商为 EBK + DC 业务类型
2
查价时没有传国籍
3
机构配置了 SubChannelID
满足以上三点 → 自动标记国籍为 CN + 标记忽略国籍（后续不过滤 RP 的国籍限制）
如何关闭：设 "NationalitySubChannelID": {} 即可。
配置地址：https://wolf.didaadmin.com/ConfigurationCenter/Editor/30/Dida.Biz.Rate.SubClientID
NationalityHackUnified 国籍 Hack 统一配置
▼
作用：当国籍被过滤时，通过配置决定最终用什么国籍去查供应商。仅用于 Rate（查价/验价） 场景。
执行逻辑：按优先级从高到低依次匹配，命中即止，输出两个结果：
  • NationalityOutput：最终用什么国籍去查供应商
  • HackLiability：因国籍问题产生争议单时的责任归属（Channel / Supplier / Dida）
优先级（从高到低）：
优先级配置节点说明 1（最高）ClientSupplierRules最细粒度：渠道 + 供应商 + 酒店国家 + 请求国籍 组合精确匹配。每条规则可单独指定 HackLiability 2ClientRules.ClientOverrides机构级统一：CS 级别未命中时，按机构统一指定国籍。可指定 HackLiability 3ClientRules.BaseSettings代码硬编码兜底：GetFromOptionsInput → GetFromCRM → CN
CS 级别匹配条件优先级：
优先级条件组合 1ClientIDList + DidaHotelCountryCode + OptionsInput 2ClientIDList + DidaHotelCountryCode 3ClientIDList + OptionsInput 4ClientIDList
HackLiability（责任方）： Channel Supplier Dida（默认）
特殊规则：当 HackLiability 为 Channel 且输出国籍与渠道输入不同时 → 返回 ChannelInput（渠道原始国籍），不使用修改后的国籍。
ClientActionStrategy（渠道级覆盖策略）
策略值含义 UseRequestNationality使用渠道请求中的原始国籍 UseDidaHotelCountryCode使用酒店所在国国籍 两位国籍码（如 KR）强制指定该国籍
可选 DidaHotelCountryMap：先按国家映射表匹配，命中则直接返回映射后的国籍；未命中再走 ClientActionStrategy。
IgnoreHackRules（跳过国籍 Hack 白名单）
配置哪些订单流程跳过 Hack；以及人工补单流程中哪些供应商必须走 Hack。
{ "BookingFlows": { "ManualRepair": { "ForceHackSupplierIDs": [429] } } }
完整 JSON 示例
{ "ClientSupplierRules": { "429": [{ "ClientIDList": ["Agoda"], "DidaHotelCountryCode": "HK", "NationalityOutput": "CN" }], "-1": [{"NationalityOutput": "ChannelInput"}] }, "ClientRules": { "BaseSettings": { "DefaultSetting": { "Steps": ["GetFromOptionsInput", "GetFromCRM", "CN"] } }, "ClientOverrides": { "YanoljaB2B": { "ClientActionStrategy": "KR", "HackLiability": "Channel" } } } }
⚠️ 待讨论：三个配置（CheckNationalityClient / SubClientID / NationalityHackUnified）之间的执行顺序尚无明确文档说明，需找开发确认。
坑位合并（RP 合并）
按房型+床型+餐型+能否取消的坑位组合，将供应商返回的 RP 做分组聚合，去除重复报价，减少渠道端计算量。
Channel.MergeRatePlan.Config RP 合并 / 轮转配置（Channel + ClientID + Format）
▼
JSON 结构：
{ "IsGlobalMergeRPEnabled": true, "GlobalMergeRPHotelRateCache": 60, "ChannelClients": { "ClientA": { "Enable": true, "CacheTimeOutMinutes": 30 }, "ClientB": { "Enable": false } } }
什么是"坑位"
渠道在展示时只固定展示几种条件的报价，通用取值组合是 房型 + 床型 + 餐型 + 能否取消。RP 合并就是按坑位常见条件组合聚合供应商的 RatePlan，去除重复报价。
聚合的维度（含 IsForceAsNonRefund）
#维度说明 2RoomTypeIDDidaRoomTypeID 3MealTypeIDDidaMealTypeID 4MealAmount餐食数量 5BedTypeIDDidaBedTypeID 6IsOnRequest是否待确认（0 即时 / 1 待确认） 7IsHourlyRoom是否钟点房 8IsNonRefundable是否不可退款 9RatePaymentTypeID支付方式 10SubClientID资源上的 ClientID 11DidaValueAddItemIDs增值服务 ID 集合 12InvoiceAcquireTypeID开票人类型 13IsForceAsNonRefund复制的不可取消 RP（天然不同组，不参与合并）
组内取值规则
OrderBy(TotalPrice).ThenByDescending(CancellationList.First().FromDate) // 取分组中价格最低、且免取时间最晚的一条
MergeRatePlanID 生成
将上述维度按固定顺序拼接，再做 Base62 编码，最终格式为 MergeRatePlanID-DidaRatePlanID，例如 4il47aNbtmi-cgestWE0GcT。
Base62 编码后不一定都是 11 位，也可能是 10 位（如 9gR7Y17hyl-adC1EHXQBuc）。
MergeRatePlanID 解码回查
可通过 MergeRatePlanInfo API 文档 将 MergeRatePlanID 解码回原始的 SupplierID、SupplierRatePlanID 等信息，方便排查合并前后的 RP 对应关系。
Hotel 级别（查价阶段执行）
售卖房型 RP 服务套餐分组聚合 + 单酒店实时报价缓存。中间层先做 MergeRatePlanInfo 的组合和 MergeRatePlanID 的构建，然后再做 RP 聚合处理。
RatePlan 级别（验价阶段执行）
售卖房型 RP 服务套餐轮转 + 缓存报价价格替换。轮转与原始 RP 验价请求并行进行，最后比较两者价格，选择最优结果返回。
不支持 RP 合并的场景
场景原因相关配置 SwitchClient不走 RP 合并模式Dida.Biz.SwitchConfig ChannelID = DidaShoppingShopping 前端多供应商并发，无法合并— 验价时使用"询价代替"的机构不走 RP 合并模式DidaAPI.Config.RPToHotelSearchV2 渠道本地缓存单天报价构建连住连住要求 RP 必须相同，合并后每天轮转出的大概率不是同一个 RP—

NonRefundFilterV2 不可取消 RP 过滤（最后一道关卡）
▼
作用：控制不可取消 RP 的露出条件，是报价输出的最后一道关卡。
JSON 结构：
{ "BroadwayTravelB2C": {}, // 空对象 = 过滤全部不可取消 RP "JTAtravelB2B": { "MaxBeforeCheckInHours": 72 // 入住前 72h 内不可免费取消 → 移除 }, "config_demo": { "MinAfterBookingHours": 3, // 下单后 3h 内不可免费取消 → 移除 "MaxBeforeCheckInHours": 24 // 入住前 24h 内不可免费取消 → 移除 } }
配置值含义 {}过滤全部不可取消 RP（包括复制出的 -N RP），只出可取消的 MaxBeforeCheckInHours: 72入住前 72h 内不可免费取消的 RP → 移除 MinAfterBookingHours: 3下单后 3h 内不可免费取消的 RP → 移除
判断逻辑（MaxBeforeCheckInHours）：
if (CheckinTime - 免费取消截止时间) < 配置小时数: → 报价过滤掉 else: → 报价正常出
或关系：MaxBeforeCheckInHours 和 MinAfterBookingHours 为或关系，满足任一条件即移除对应 RP（不是同时满足才移除）。
执行时机（知识库已确认）
1
RP 合并 → RP 过滤 → 复制不可取消 RP → 不可取消过滤（最后一道关卡）
2
不可取消过滤会对已完成合并、过滤和复制的全部 RP 进行过滤
3
配置为 {}（空对象）→ 所有不可取消 RP（包括复制出的 -N RP）全部被过滤，仅输出可取消 RP
配置地址：https://wolf.didaadmin.com/ConfigurationCenter/Editor/30/DidaAPI.Config.NonRefundFilterV2
OccupancyFilterConfig 入住人数过滤
▼
作用：过滤餐型/人数不一致的报价。按「床型筛选」和「餐食筛选」两步判断。
床型筛选
系统计算实际入住人数（成人 + 可能包含的儿童），与每种床型的默认可入住人数对比，可入住人数 < 实际入住人数 → 该 RP 排除。
餐食筛选
系统比较套餐内早餐份数（MealAmount）与实际入住人数：
  • 餐数 < 实际入住人数 → 排除
  • "不含餐"不做检查直接保留
  • 餐数信息缺失 → 排除（不确定能否满足需求）
儿童是否计入人数
由配置项 MealType（餐型）和 BedType（床型）控制：0 = 不含儿童，1 = 含儿童。
配置地址：https://wolf.didaadmin.com/ConfigurationCenter/Editor/30/Dia.Biz.Rate.OccupancyFilterConfig
LowBalanceSwitchToCacheClientScopes 低余额降级切缓存
▼
作用：供应商余额不足时切换为缓存报价，降低实时请求量，避免因余额不足导致查价失败。
配置字段：SwitchCacheBalanceBaseLineCNY（人民币阈值，默认 500）+ ClientIDList（机构名单）
执行逻辑
1
后台 Job 持续监控名单内机构的财务账号余额
2
余额 < 阈值 → 多酒店/单酒店实时查询自动切换为缓存查询
3
余额恢复至阈值以上 → 恢复为原先的查询方式（实时就实时，缓存就缓存，不主动覆盖）
④ 输出策略
RP 经过以上环节后，最终输出前的最后处理：坑位报价数量控制、最优取消政策、复制不可取消 RP 等。

TopCountForBreakfastCancellation 坑位报价数量 + 最优取消政策
▼
目的：按「餐型 + 取消政策」坑位控制报价输出数量，2.0 额外输出「最优取消政策」报价，满足 B2C 用户对"临近入住仍可退"的高溢价需求。
与 RP 合并互斥：一旦机构开了 RP 合并，此配置完全不生效。要用最优取消政策，必须主动删除 RP 合并的配置。原因：RP 合并每组只留 1 条（价格最低），无法额外输出"价格更高但取消政策更好"的报价。
配置格式演变
版本格式含义 1.0（老配置）"1,1"第 1 位：聚合房型；第 2 位：未聚合 RP。每坑位各出 N 条最低价 2.0（新配置）"1,1,1,1"第 1、2 位同上；第 3 位：聚合房型额外加最优取消政策；第 4 位：未聚合 RP 额外加最优取消政策
Wolf V2 迁移后（每个位置拆成独立字段）
老配置位置Wolf V2 Key含义 第 1 位MappedRoomTypeTopCountForBreakfastCancellation已匹配房型，按「餐型 × 取消政策」4 坑位各出 N 条最低价 第 2 位UnmappedRoomTypeTopCountForBreakfastCancellation未匹配房型，同上 第 3 位MappedRoomTypeTopCountForOptimalCancellationBreakfast已匹配房型，额外按最优取消政策（取消截止日期最晚优先）再取 N 条 第 4 位UnmappedRoomTypeTopCountForOptimalCancellationBreakfast未匹配房型，同上
⚠️ 待确认：Wolf V1 和 Wolf V2 的配置是否同时生效，还是只取其一，需找开发确认。

DuplicateRefundableAsNonRefundable 复制可取消 RP 为不可取消
▼
目的：将原本可取消的 RP 复制一份，标记为不可取消，一并输出给渠道，增加渠道的报价选择。
逻辑
1
仅在单酒店实时查价中生效（酒店级别）
2
将可取消的 RP 复制一份，标记为不可取消（IsForceAsNonRefund = True）
3
复制后的 RP ID 格式：原RPID + "-N"（如 123456-N）
4
复制生成的 RP 不参与后续 RP 合并，作为独立 RP 单独输出
与 RP 合并的关系
复制出的不可取消 RP 因 IsForceAsNonRefund 字段值与原 RP 不同，在 RP 合并时天然分属不同组，不会被合并到一起。
执行顺序（知识库已确认）
RP 合并 → RP 过滤 → 复制不可取消 RP → 不可取消过滤（最后一道关卡）
复制出的不可取消 RP（IsForceAsNonRefund=True，RPID 后缀 -N）不参与 RP 合并（因为 IsForceAsNonRefund 字段值不同，天然分属不同组），作为独立 RP 单独输出。
⑤ 返回渠道报价
RP 经过以上所有环节后返回给渠道。验价阶段遵循相同模式，差异在于多了查价缓存对比。
配置地址：https://wolf.didaadmin.com/ConfigurationCenter/Editor/30/Channel.DuplicateRefundableAsNonRefundable

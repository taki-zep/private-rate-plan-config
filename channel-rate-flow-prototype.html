CheckNationalityClient 强制检查国籍（DidaAPI ONLY）
▼
控制 ARI 和 Rate 场景下是否检查国籍限制。开启后请求无国籍直接报错，后续配置不执行。
ARI + Rate DidaAPI ONLY 默认：否
Rate 场景逻辑 ▼
配置为否（默认）→ Nationality Free：国籍被过滤时直接返回报价，不执行 NationalityFilter
配置为是 → 开启国籍限制：检查 RP 的售卖国籍是否匹配，不匹配的 RP 被过滤
配置示例 ▼
渠道: DidaAPI，供应商: 429 (DaoLv)，国籍: ID，配置为 Yes → 该组合执行国籍限制检查
SubClientID 忽略国籍限制（NationalitySubChannelID）
▼
为机构指定子渠道，控制查价时是否忽略国籍限制。应用于 ARI 和 Rate 两个场景。
配置地址：wolf.didaadmin.com/.../SubClientID
ARI + Rate 四档国籍控制
四档说明 ▼
档位值含义 None空数组不限制国籍 International["2"]外宾：允许卖其他国籍 RP Domestic["3"]内宾：只卖酒店国籍 RP China["4"]中宾：允许 CN/TW/HK RP
触发条件（同时满足） ▼
1
供应商为 EBK + DC 业务类型
2
查价时没有传国籍
3
机构配置了 SubChannelID
满足以上三点 → 自动标记国籍为 CN + 忽略国籍标记（后续不过滤 RP 的国籍限制）
JSON 结构 ▼
{ "SubChannelConfigs": { "DidaOpaq": { "NationalitySubChannelID": { "None": [], "International": ["2"], "Domestic": ["3"], "China": ["4"] } } } }
如何关闭：设 "NationalitySubChannelID": {} 即可。

▼

Rate only 三级优先级 含 HackLiability
优先级与输出 ▼
匹配输出两个结果：NationalityOutput（用什么国籍查供应商）和 HackLiability（争议单责任方）
优先级节点说明 1（最高）ClientSupplierRules渠道+供应商+酒店国家+请求国籍 精确匹配 2ClientOverrides机构级统一指定国籍 3BaseSettings代码硬编码兜底：OptionsInput → CRM → CN
特殊规则：HackLiability = Channel 且输出国籍 ≠ 渠道输入时 → 返回 ChannelInput（渠道原始国籍）
CS 级别匹配条件 ▼
优先级条件组合 1ClientIDList + DidaHotelCountryCode + OptionsInput 2ClientIDList + DidaHotelCountryCode 3ClientIDList + OptionsInput 4ClientIDList

策略值含义 UseRequestNationality使用渠道请求中的原始国籍 UseDidaHotelCountryCode使用酒店所在国国籍 两位国籍码（如 KR）强制指定该国籍
可选 DidaHotelCountryMap：先按国家映射表匹配，命中则直接返回映射后的国籍；未命中再走 ClientActionStrategy。

② 坑位合并（RP 合并）
按房型+床型+餐型+能否取消的坑位组合，将供应商返回的 RP 做分组聚合，去除重复报价，减少渠道端计算量。
Channel.MergeRatePlan.Config RP 合并 / 轮转配置（Channel + ClientID + Format）
▼
按坑位条件组合聚合供应商的 RatePlan，去除重复报价。合并后给渠道的 RatePlanID 为 Base62 编码的 MergeRatePlanID。
配置地址：wolf.didaadmin.com/.../MergeRatePlan.Config
查价+验价+下单 与 TopCount 互斥 7 个渠道已适配
聚合维度 + 取值规则 ▼
#维度说明 2RoomTypeID房型 ID 3-4MealTypeID + MealAmount餐型 + 份数 5BedTypeID床型 6IsOnRequest是否待确认 7IsHourlyRoom是否钟点房 8IsNonRefundable是否不可退款 9RatePaymentTypeID支付方式 10SubClientID子渠道 11DidaValueAddItemIDs增值服务 ID 12InvoiceAcquireTypeID开票人类型 13IsForceAsNonRefund复制的不可取消 RP（天然不同组）
OrderBy(TotalPrice).ThenByDescending(CancellationList.First().FromDate) // 取分组中价格最低、且免取时间最晚的一条
MergeRatePlanID 生成与解码 ▼
维度按固定顺序拼接 → Base62 编码 → 格式 MergeRatePlanID-DidaRatePlanID，如 4il47aNbtmi-cgestWE0GcT。编码后可能 10 或 11 位。
可通过 MergeRatePlanInfo API 解码回原始的 SupplierID、SupplierRatePlanID 等信息。
各阶段执行差异 ▼
查价（Hotel 级）：RP 服务套餐分组聚合 + 单酒店实时报价缓存
验价（RatePlan 级）：RP 轮转 + 缓存报价价格替换，与原始验价请求并行进行
下单（Booking 级）：不再轮转，直接验价；验价无房即预定失败
不支持 RP 合并的场景 ▼
场景原因相关配置 SwitchClient不走 RP 合并Dida.Biz.SwitchConfig DidaShopping前端多供应商并发— 验价时"询价代替"不走 RP 合并RPToHotelSearchV2 渠道缓存单天构建连住合并后每天 RP 不同—
相关配置 + 适配渠道 ▼
配置 Key说明 MergeRatePlanDidaHotel.Config酒店维度 RP 合并（Dolphin） RedisConnectionString.Channel.MergeRatePlanDataRP 合并 Redis 连接串（Dolphin）
已完成适配的渠道：DidaApi、Agoda、SnapTravel、DerbySoft、飞猪国际、美团国际、去哪儿国际

NonRefundFilterV2 不可取消 RP 过滤（最后一道关卡）
▼
控制不可取消 RP 的露出条件，是报价输出的最后一道关卡。对已完成合并、过滤和复制的全部 RP 进行过滤。
配置地址：wolf.didaadmin.com/.../NonRefundFilterV2
最后一道关卡 OR 关系
配置值与含义 ▼
配置值含义 {}过滤全部不可取消 RP（包括 -N RP），只出可取消的 MaxBeforeCheckInHours: 72入住前 72h 内不可免费取消 → 移除 MinAfterBookingHours: 3下单后 3h 内不可免费取消 → 移除
或关系：满足任一条件即移除（不是同时满足才移除）
判断逻辑 + 执行时机 ▼
if (CheckinTime - 免费取消截止时间) < 配置小时数 → 过滤 else → 正常输出
1
RP 合并 → RP 过滤 → 复制不可取消 RP → 不可取消过滤（最后一道）
2
配置为 {} → 所有不可取消 RP（含 -N RP）全部被过滤
OccupancyFilterConfig 入住人数过滤
▼
过滤餐型/人数不一致的报价。按「床型筛选」和「餐食筛选」两步判断。
配置地址：wolf.didaadmin.com/.../OccupancyFilterConfig
两步筛选 含儿童控制
床型筛选 + 餐食筛选 ▼
床型筛选：实际入住人数（成人 + 儿童）vs 床型默认可入住人数，可入住 < 实际 → 排除
餐食筛选：早餐份数 vs 实际入住人数
  • 餐数 < 实际人数 → 排除
  • "不含餐"不做检查直接保留
  • 餐数信息缺失 → 排除
儿童计入规则 ▼
由 MealType（餐型）和 BedType（床型）控制：0 = 不含儿童，1 = 含儿童
LowBalanceSwitchToCacheClientScopes 低余额降级切缓存
▼
供应商余额不足时切换为缓存报价，降低实时请求量，避免查价失败。余额恢复后回到原先方式。
配置地址：wolf.didaadmin.com/.../LowBalanceSwitchToCache
后台 Job 监控 自动恢复
配置字段 + 执行逻辑 ▼
配置字段：SwitchCacheBalanceBaseLineCNY（阈值，默认 500）+ ClientIDList（机构名单）
1
Job 持续监控名单内机构余额
2
余额 < 阈值 → 实时查询切换为缓存查询
3
余额恢复 → 恢复为原先方式（实时就实时，缓存就缓存，不主动覆盖）

术语速查
报价全链路涉及的核心概念，按出场顺序排列。
ARI Availability / Rates / Inventory
▼
批量询价场景。用户在酒店列表页选择日期、人数后，系统对多个酒店同时发起查价请求。返回的是酒店级别的汇总数据（最低价、房型数量等），用于列表展示。
酒店级别批量请求
Rate 单酒店精确查价 / 验价
▼
单酒店详情页场景。用户点击某个酒店后，系统对该酒店发起精确查价，返回每个 RP 的详细信息（价格、取消政策、餐型等）。验价也是 Rate 场景，用于确认价格有效性。
RP 级别精确请求
ARI vs Rate 的区别：ARI 管"有哪些酒店、最低价多少"；Rate 管"这个 RP 具体多少钱、什么条件"。很多配置只作用于 Rate 场景，因为 ARI 阶段信息还不够细。
RP (RatePlan) 报价方案
▼
供应商返回的一个可售房型报价，包含：房型 ID、床型、餐型、价格、取消政策、入住限制等。一个酒店可以有多个 RP（如含早可退、不含早不可退等）。
最小报价单元
RPID：每个 RP 的唯一标识。合并后生成 MergeRatePlanID（Base62 编码），格式如 4il47aNbtmi-cgestWE0GcT。
坑位 房型+床型+餐型+取消政策的组合维度
▼
RP 合并时用来分组的维度组合。同一坑位内的多个 RP 只保留一条（最低价），不同坑位的 RP 互不影响。
维度示例 RoomTypeID大床房、双床房 BedTypeID大床、双床、三床 MealTypeID + MealAmount含早×2、不含早 IsNonRefundable可取消、不可取消
坑位合并后，同一坑位只出一条报价。TopCount 控制每个坑位出几条，最优取消政策额外再出一条。
ClientID 机构 / 渠道标识
▼
每个接入 Dida 的渠道/机构有唯一 ID，如 DidaOpaq、AgodaUK、A__map。大部分配置按 ClientID 维度生效，不同机构可以有不同配置。
配置维度机构隔离
Wolf / Dolphin Dida 配置中心
▼
Wolf：机构级配置中心，按 ClientID + Key 存储。大部分业务配置在这里。
Dolphin：全局配置中心，不按机构区分，存 Redis 连接串等全局参数。
Wolf = 机构级Dolphin = 全局
Wolf V2 API：POST 到 wolf-caller-api.didaadmin.com，需要 clientIds 参数。
Dolphin API：GET 到 wolf-v3-api.didainternal.com:8081，需要 Bearer Token。
